GitHub Field Guide

Learn GitHub by exploring the real One Place project—no code to write, no account required for this practice, and no changes to publish. Four short missions, one at a time.

Your role: Understand what's proposed, tested and published. GitHub records the evidence; it doesn't decide what One Place should become. Your choice remains yours. Never post passwords, personal health records or family information in a public repository.

Know where the work lives

02 · SAFELY PROPOSE A CHANGE

Understand a draft pull request

A branch is a separate line of development. A pull request (PR) proposes changes; it is not itself a live-site release.

Look at the real project

Open historical PR #53. Notice its changed files, test discussion and merge history. A draft PR stays separate from the live source until reviewed and intentionally merged.

03 · FOLLOW THE EVIDENCE

Understand a red X in Actions

A red X means a workflow failed. It tells us to inspect the logs; it does not automatically mean the public website stopped working.

Look at the real project

On November 12, a PR #54 test run reported 682 passing tests and one failure. The failure was a test choosing between two links with the same name. We corrected the test selector on the draft branch. This is a dated case study; GitHub's current statuses may have changed.

04 · DECIDE WHAT GETS PUBLISHED

Verify a real release

Founder approval authorizes publication. The merge changes main; GitHub Pages deploys it; live and regression checks show whether the release worked.

Look at the real project

Compare PR #53 with its Pages deployment and post-merge regression. That release passed 673 tests and the exact published-file check. This is stronger evidence than a green icon alone.
